## Reviewed adjudication and initial implementation

Astra and actual Claude reviewed this packet independently. Their bounded reports are in `docs/qualification/task-replacement-correction-plan-astra-r19.md` and `task-replacement-correction-plan-claude-r19.md`. Their decisions are source/design review, not behavioral or live acceptance.

- C1 restores only an absent exact scope. Trace input intents without independent canonical Core proof are excluded from actionable context and acknowledgement. They remain historical evidence; pending mail uses the normal authorization/commit path. A concise recovery notice names the missing proof. Fully tombstoned scopes and deliberate fresh epochs are not resurrected.
- C2 stages deterministic plan-resolution mail before clearing the exact Question's gate. All closed approval Questions use that resolver, including startup repair. Rejection preserves planning mode.
- C4 binds the model hold to the assignment and captures the exact worker reservation. Resume records deterministic mail before clearing the hold; no hold means no-op. Independent composer/autonomy pauses are untouched.
- C5 persists the merged flag with accumulated state. A legacy admitted row preceding a later saved step is already merged. C7 retries the failed step under a new linked workflow invocation, retaining completed merged rows by reference rather than replaying their effects. Uncertain children remain resumable.
- C6 starts the wall-clock budget when the workflow requests the child, before its durable admission. It includes queue time, pause and downtime. Stop, wait and recovery never renew it. Absent timeout is unbounded; an explicit zero, NaN or infinity is invalid. The existing conversation owner uses a timer handle and its cancellation path; cleanup may complete later or stay unknown. No generic driver or workflow scheduler is added.
- C8 retains strict R2 settlement and restart holds. Unknown cancellation processing retires its waiter and keeps only a passive, exact-member observation callback. Genuine later proof can finish cancellation. The captured raw result is available as bounded **nonfinal backend evidence**, with `pending=true`, no terminal timestamp and no collection acknowledgement. Fresh receipts never settle older unknown incarnations.
- Existing active-at-cancellation membership remains strict. Claude suggested counting a natural external acknowledgement as settlement; Astra's earlier explicit R2 interpretation rejects that for members active at admission closure. Already-terminal-before-request outcomes remain historical. No predicate was weakened.

An optional human clarification is pending: whether to amend R2 to permit an explicitly authenticated restart naming all unresolved handles/episodes. No such exception is implemented or inferred from elapsed time. Current controls/status/results remain available for human inspection while the cancellation hold remains.

## Original semantic question supplied to reviewers

R2 explicitly forbids external acknowledgement as physical-cleanup proof, says uncertain waits return without a terminal timestamp, and forbids restart until necessary settlement is known. Claude correctly identifies that the present consequence is a permanently inaccessible parent. Please resolve the smallest contract-consistent path: can a retired parent accept explicit human inspection while retaining a cancellation/admission hold, or does allowing deliberate human continuation require amending R2? Do not recommend silently marking descendants settled or automatically launching a successor.

For persistent native work, a fresh redelivery result must not settle an unknown previous incarnation. The current code hides that fresh result and leaves an unresolvable wait. Define whether recording backend completion plus a separate unresolved physical-settlement state is sufficient, and what human/owner observation is needed to finish/retry. No global exactly-once mechanism or PID-only recovery.

C6 is a declared execution-limit timer inside the existing conversation owner, not a workflow scheduler or generic task driver. Please flag a simpler existing mechanism if available. Cancellation settlement remains the existing owner path.
