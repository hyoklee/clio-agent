**Verdict: NO-GO on this source, with the architecture itself approved in principle.** The replacement is faithful to the plan's shape and is genuinely simpler than what it replaced. There is one typed record for all seven kinds (`src/clio_agent/arc/task_types.py:134`), one serialized Core writer with passive rebuildable indexes (`src/clio_agent/gact/task_history.py:60`), one recipient-input commit as the sole acknowledgement (`task_history.py:366`, `session_mail.py:181`), one admission path where producers only persist and signal (`turn_runner.py:63`, `conversations.py:88`), exactly one SDK driver per accepted task (`native_tools.py:539`, `external_tasks.py:522`), and a transport wrapper that composes through the supported session-class hook rather than patching (`tools/task_transport.py:119`). Sessions are first-class addressable work: spawn mints a Subagent handle plus a reply-only grant (`conversation_assignments.py:449`), messaging resolves handle or session through the same access check (`task_declarations.py:150`, `session_mail.py:291`), and parents collect children, Questions, Shell and MCP through one mixed wait whose collection flows into the recipient-input commit (`task_operations.py:217`, `task_declarations.py:53`, `agents/clio_react_record.py:673`). ask_user posts a durable handle immediately with no worker and the answer wakes the owner only through Core mail (`task_declarations.py:259`, `questions.py:284`, `task_publication.py:26`). Authorization precedes disclosure and observe-only views are redacted (`task_access.py:90`, `task_access.py:175`). GACT consumes these routes through one operational-state decoder and a cancel dialog that names the task and warns about descendants (`external/gact-tui/packages/core/src/v3/schemas.ts:127`, `web/src/routes/runs-page.tsx:711`, `session-access.tsx:38`). This is a source-level judgment only. Every behavioral gate in the ledger remains unexecuted, no Q1 to Q9 or R1 to R6 evidence exists, and the R19 to R26 correction documents the ledger cites are absent from this snapshot, so nothing here is runtime acceptance.

**Where it has started to regrow an engine, and the defects that block approval.** The replacement surface is roughly 14,600 non-blank lines across about 50 modules, and its complexity concentrates in two places the plan explicitly warned against. First, `CoreRecovery.defer` has become a general cross-owner retry queue: more than thirty distinct deferral identities are registered from native, external, conversation, Question, A2UI and workflow owners, each wrapped in a repeated `try/except Exception: defer` idiom. Because a permanently failing action is retried forever at 30 second backoff and `drain()` awaits the worker without exit (`core_recovery.py:55`, `core_recovery.py:63`), any owner that defers a validation error, not a recording error, hangs orderly shutdown. That exact mistake exists in `conversation_controls.cancel` (`conversation_controls.py:339`): a ValueError from `require_execution_owner` on a historical or non-local assignment is swallowed, reported to the caller as `cancellation_requested: True, recording: "unconfirmed"`, and parked as a reconcile that can never succeed. Second, the "passive" record carries execution policy: `TaskSnapshot.validate_custody` special-cases the `connected_data_continue` tool by name (`task_types.py:203`), and `_cancel_subtree` is a 300-line re-arming watcher with nested closures (`conversation_controls.py:487`). Further concrete defects: the any-wait short-circuits on an unauthorized member because the unavailability row counts as an outcome (`task_operations.py:243`, `task_operations.py:279`); a conversation assignment's `attention_episode` is set but never cleared while non-terminal (`conversation_recovery.py:142`), so a parent's every subsequent wait on it returns immediately; `restore` replays every semantic event in the store on each writer-failure recovery while holding the writer lock (`task_history_projection.py:212`, `core_recovery.py:73`); and the writer reaches into ARC privates (`task_history.py:779`, `core_recovery.py:69`). GACT still models the retired registry (`agent-task-domain.ts:3` documents fields the new view never emits at `routes/tasks.py:109`). My recommendation is to fix the defer-on-validation and any-wait bugs, bound the recovery queue to recording failures only, and then run the ledger families before any release.
