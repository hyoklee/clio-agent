# Independent Claude Code Fable review R27

Core 5eab9ef8; GACT 30df56ed. Committed source, acceptance ledger and correction maps; neutral two-paragraph brief; read-only source review.

**Verdict: the architecture is coherent and faithful to the plan, and it is genuinely simpler in kind than what it replaced, but I would not approve this source as-is.** There is one immutable `TaskSnapshot` for all seven kinds (`src/clio_agent/arc/task_types.py:134`), one serialized Core writer with passive rebuildable indexes (`src/clio_agent/gact/task_history.py:60`), one mailbox whose only acknowledgement is the recipient-input commit (`src/clio_agent/gact/session_mail.py:181`), and no scheduler, transition table or cross-owner reconciler anywhere. Sessions really are addressable assignments: `send_agent_message` resolves a handle to its owning session and checks the message right, children get only a delegation-reply grant (`conversation_assignments.py:449`), and pause/resume/restart/cancel are Core-recorded commands on the same snapshot. Questions are correct too: `ask_user` posts through the short built-in boundary and returns immediately (`task_declarations.py:276`), an answer publishes an owner notice that wakes an idle runner, and an explicit `wait_tasks` collects it through `_collected` and the tool-observation commit (`task_declarations.py:53`, `agents/clio_react_record.py:665`), so the "asynchronous handle gathered by a shared wait" story holds end to end. Native and external owners each keep exactly one `ToolTask.result()` driver and the SDK adapter is narrow (`tools/task_client.py:152`, `tools/task_transport.py:95`). The GACT side is a thin passive projection with an honest state decoder and a descendant-cancel warning. Maintainability is the weaker axis: the task/conversation/native layer is still roughly 17,000 lines across 54 modules, the `Conversations` owner is split into three "free functions taking self" files to dodge the size guard, and `CoreRecovery` holds dozens of string-keyed deferred closures that together behave like a small reconciliation engine even though Core stays authoritative. That is heavy, but it is not the old engine rebuilt.

**The consequential defect is a hot re-admission loop on any turn that fails or is vetoed before the model input is committed.** The trigger mail is acknowledged only inside `commit_input`, which runs just before the first model call. If the turn ends earlier, because a `UserPromptSubmit` hook returns `blocked` without holding the mail (`hooks/user_prompt.py:93`) or because setup raises a consumed error such as no resolvable agent (`turn.py:426`, `turn.py:513`), the trigger stays pending and eligible. `_finish_segment` then either yields because eligible mail exists or marks the assignment failed (`conversation_assignments.py:222`, `:251`), `_run` signals the runner (`conversations.py:706`), the pump loops immediately (`turn_runner.py:97`), and `_admit` re-stages the same trigger, minting a new linked assignment whenever the last one is terminal (`conversations.py:290`). Nothing in `eligible()` consults session error status, and the gate only reads `execution_blocked_reason`, so a persistent misconfiguration produces an unbounded stream of failed Session or Subagent snapshots and parent `task_result` notices. The only hold paths are Stop and cancel (`conversations.py:672`). Two lesser items: `wait` returns immediately for an all-wait as soon as any member carries an attention episode (`task_operations.py:242`, `:296`), which is by plan but will make a model's repeated waits spin until an owner clears the episode; and the compatibility REST listings still scan the whole tree with `limit=10000` per request (`routes/tasks.py:231`, `:242`, `:313`). Everything above is source inspection only. No test exercises pre-commit failure re-admission, the ledger records R27 cases as unexecuted, and Q1 through Q9 and R1 through R6 have not run, so this is neither runtime acceptance nor a release-readiness judgment.
