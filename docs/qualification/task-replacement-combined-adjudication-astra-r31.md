**The inline-start/readiness-future proposal is appropriate.** Create the readiness future, launch agent construction and provider discovery as today, then directly `await task_runtime.start(app)` in the lifespan. Resolve readiness after successful startup. Agent construction can remain parallel and await readiness before signalling pending sessions.

Startup failure must settle readiness and unwind partial startup and producers. Crucially, wrapping `start(app)` or `close(app)` in `asyncio.shield(...)` would create another task and recreate the context-ownership problem. Shielding a readiness **future** is different. This requires no new lifetime coordinator.

I would amend Fable’s other conclusions as follows:

- **Permanent submission history is not an established defect.** Unlimited canonical Core history is required, and R2 explicitly says to measure replay before optimizing. Also, [submission index repair](C:/Users/jaime/.codex/worktrees/agent-facing-async-tasks/clio-agent/src/clio_agent/gact/task_history_projection.py:307) compares existing contents and writes only differences; it does not rewrite every submission index on every boot. Exact submission resolution already uses a direct lookup.
- **F03 still needs realistic evidence.** Measure tool-call volume and payloads, replay, migration’s additional pass, index verification/reconstruction, memory and narrow-query work. Retained-task count alone misses this workload. Preserve canonical history; optimize passive projections only if measurements justify it.
- **Stop retaining uncommitted accepted input is correct.** Later eligible mail resumes retained input in accepted order. Sending B does not withdraw A. Cancellation or withdrawal must remain explicit.
- **Fable’s context-clear finding is partly correct.** Stale activity needs correction; refusing to reinstall the old epoch’s output/context is intentional.
- **The polling findings need separation.** Whole-tool 5 ms liveness polling leaves the accepted R26 removal incomplete. The 100 ms checks in `call_on_application` serve cooperative cancellation; they are not whole-history polling. Do not remove them without preserving cancellation notification.
- **Matching control-hold release is a contract issue**, not merely cosmetic cleanup: R2 explicitly requires releasing matching holds after reconciliation. Fanout-resource retirement should likewise preserve concurrency correctness.
- **Lock contention belongs in Q8 measurement.** The subscriber-principal assumption deserves targeted hardening before multi-human operation, but this review establishes no current single-human disclosure. The missing-session guard is a small typed-error correction. Splitting `Conversations` differently would not resolve these defects.

The architecture does not need another coordinator, registry or scheduler. It needs these ordering and retirement corrections, followed by the outstanding qualification.
